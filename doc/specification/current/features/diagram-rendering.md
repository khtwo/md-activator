# Diagram Rendering & Editing

_[← Application Features index](../application-features.md)._ Mermaid diagram rendering and auto-repair, the shared diagram canvas zoom/pan controller, and maxGraph XML rendering, routing, and inline editing. The diagram write-back/repair endpoints are specified in [server-api.md](server-api.md).

## Mermaid Rendering
- Fenced code blocks whose info string is `mermaid` are converted into Mermaid render containers. The fence may use backticks (```` ``` ````) or tildes (`~~~`), the info string is matched case-insensitively (`mermaid`, `MERMAID`, etc.), and the closing fence must match the opening fence character; an unterminated fence is not treated as a diagram block.
- Raw diagram blocks whose first line is a recognized Mermaid diagram declaration are converted into Mermaid render containers. A declaration line is the diagram keyword alone, or with only its allowed first-line qualifier — a `flowchart`/`graph` direction (`TB`/`TD`/`BT`/`RL`/`LR`) with an optional trailing `;`, a `pie` `showData` and/or `title <text>`, or a `gitGraph` direction (`TB`, `BT`, `LR`, or `RL`) with an optional trailing `:` — and nothing else on the line. Recognition is case-insensitive. Prose lines that merely begin with a diagram keyword followed by ordinary text (for example a wrapped sentence starting with `graph`, `pie`, or `classDiagram`) are not treated as diagrams.
- Mermaid diagram source is escaped as text inside the render container before client-side rendering.
- Each Mermaid render container carries its originating source line and occurrence-index metadata (`data-mermaid-line`, `data-mermaid-index`) for both fenced and raw blocks so the browser can locate the exact source block when writing an edit back.
- The browser UI initializes Mermaid and runs Mermaid rendering after each successful markdown render.
- Rendered Mermaid entity boxes (nodes) of node-bearing types — `flowchart`, `erDiagram`, `classDiagram`, and `stateDiagram`/`stateDiagram-v2` — can have their titles edited inline. Double-clicking a box opens a multiline textarea editor positioned over the box, pre-filled with its current display title; saved line breaks are stored as Mermaid `<br>` breaks. The editor opens at a minimum editing area of **150 wide × 50 high** (SVG user-space units, floored up from the box only when the box is smaller), so a small node still gets a usable editor. On blur with changed text the new title is persisted to the originating Mermaid source block as a stable-identifier display-label alias (`A["label"]` for flowchart, preserving the node's existing shape; `ENTITY["label"]` for erDiagram; `class Name["label"]` for classDiagram; for stateDiagram a `<id> : <text>` description line — replacing an existing description, replacing the quoted text of a `state "..." as <id>` alias, or appended when the state shows its bare id), preserving the source identifier and the rest of the block; the diagram then re-renders. Titles needing quoting are written as quoted labels, an empty title is treated as a cancel, and an unchanged title closes the editor without a save request. Other diagram types and nodes whose source identifier cannot be recovered from the rendered SVG are left non-editable; for stateDiagram the `[*]` start/end markers and composite-state entry points (label-less pseudo-states) and composite parent states are non-editable.
- Rendered Mermaid edge labels (relationship/link/transition labels) of the same node-bearing types can also have their titles edited inline. The editor opens by double-clicking the edge label **or** the edge connector line itself — a wide transparent hit band (`.mermaid-edge-hit`, mirroring maxGraph's edge hit band) is laid over each edge connector path so the thin line is easy to double-click — so an untitled edge, which renders only an empty, position-less label group (it carries no transform and sits at the svg origin — *not* at the edge midpoint) and otherwise offers nothing to double-click, can still be given a title from the canvas. Double-clicking opens a multiline textarea editor (pre-filled with the current label text, empty for an untitled edge): a **titled** edge's editor opens over its rendered label box (mapped from the label group's local coordinates into the svg's user space), while an **untitled** edge's editor is anchored at the projected double-click point. The editor opens at a minimum editing area of **150 wide × 50 high** (SVG user-space units): a titled edge's label box is floored up to that size, and an untitled edge's blank editor uses 150×50 as its default box so it stays centred on the click point. The editor `foreignObject` is appended to the svg root so it renders **above** the diagram's nodes (which mermaid paints after the edge labels) and is never occluded by a node. Saved line breaks are stored as `<br>`. On blur with changed text the new label is persisted to the originating Mermaid source block: flowchart links replace an existing `|label|` pipe or inline `-- label -->` text, or add a `|label|` to a bare arrow (quoted when needed); erDiagram relationships replace the quoted text after the `:`; classDiagram relationships replace or append the literal text after the `:`; stateDiagram transitions replace or append the literal text after the `:` on the `<src> --> <tgt>` line. The edge to rewrite is located by relationship ordinal for erDiagram/classDiagram, by source-order transition ordinal for stateDiagram (recovered from the rendered `edge<N>` path id), and by `(source, target, occurrence)` for flowchart (endpoints recovered from the rendered edge path id, disambiguated against the known node ids). Flowchart `&` multi-node links and link operators the rewriter cannot safely parse, and stateDiagram self-loop transitions (which mermaid renders ambiguously, without a recoverable ordinal), are left non-editable on both the label and the line / fail with an error rather than corrupting the source.
- Saving an edge title edit with an empty value clears the edge's label (instead of cancelling): the flowchart link drops its `|label|` pipe or inline text back to a bare arrow (preserving the link's line style and arrowheads), and erDiagram/classDiagram/stateDiagram drop the `: label` (and its colon) back to the bare relationship/transition. The now-unlabeled edge stays present and re-editable by double-clicking its connector line. Only the empty string clears; an unchanged value (including an already-empty edge left empty) closes the editor without a write, and a whitespace-only value is a normal label. (Entity-box/node titles are unaffected — an empty node title is still a cancel.)
- Successful Mermaid entity-box and edge title changes are tracked in the shared browser-session edit history alongside maxGraph edits: Ctrl+Z reverts the latest saved Mermaid title and Ctrl+Y reapplies it. A pointer-down on an editable node, an edge label, an editable edge connector line, or inside an open Mermaid title editor does not start a canvas pan, and a click on empty canvas background commits the open editor before panning. Pressing Escape while a Mermaid title editor is open commits it the same as blurring — a changed title is saved and the editor closes, an unchanged one just closes (Enter still inserts a newline).
- Rendered Mermaid entity boxes (nodes) of the node-bearing types (`flowchart`, `erDiagram`, `classDiagram`, `stateDiagram`/`stateDiagram-v2`) support multi-selection on the canvas, mirroring the maxGraph selection affordance. Holding **Shift** shows a crosshair and a pointer drag draws a rubber-band selection box (instead of panning); on release every selectable node whose box intersects the box is **added** to the selection (repeated Shift-drags accumulate across regions; Shift never clears). Holding **Ctrl/Cmd** and left-clicking a node **toggles** its membership (no drag, no pan). **Escape** clears the whole selection. Selection is **nodes only** — edges are never selectable — and has no group move (mermaid nodes have no stored size/location). Only nodes whose source identifier is recoverable from the rendered SVG are selectable, and label-less stateDiagram pseudo-states (`[*]` start/end markers and composite entry points) are excluded — the same set that is title-editable. The marquee box and each node box are compared in the svg's user space (the same projection the edge-title editor uses, cancelling the zoom/pan transform and the root `viewBox`). A selection-modifier pointer-down takes precedence over the zoom/pan controller (a capturing handler on the svg stops it reaching the controller's pan handler) so it does not start a pan; a plain background drag still pans and the selection persists. Selection is view-only (never written to the markdown file) and per render: a real re-render rebuilds the SVG and resets the selection, while an in-app no-op reload (the rendered diagram is left in place) does not re-bind or duplicate the selection handlers. (Node selection exists to drive batch delete, planned in a later increment.)
- Each rendered Mermaid canvas of a node-bearing type (`flowchart`, `erDiagram`, `classDiagram`, `stateDiagram`/`stateDiagram-v2`) shows a small top-right toolbar with an **Add Node (`+`)** and an **Add Edge (`→`)** button (mirroring the maxGraph Add controls; canvases of unsupported types get no toolbar). **Add Node** appends a new isolated node titled "New" to the originating source block with a server-generated unique id (`New_1`, `New_2`, …) — `<id>["New"]` for flowchart/erDiagram, `class <id>["New"]` for classDiagram, and a `<id> : New` description line for stateDiagram — then re-renders (mermaid auto-lays-out the whole diagram, since mermaid nodes have no stored position). **Add Edge** enters a crosshair edge-pick mode: the first node click sets the source (highlighted amber), the second sets the target, and a new edge is appended — a bare `<src> --> <tgt>` connector for flowchart/classDiagram/stateDiagram (titled afterward via the edge-title editor), or a `<src> }o--o{ <tgt> : ""` relationship (default cardinality, empty editable label) for erDiagram — then re-renders. A self-loop (target = source) is ignored, and Escape, an empty-canvas click, or re-clicking `→` cancels the mode. While edge-pick mode is active the node-selection modifiers are inert, and an add-control or pick pointer-down does not start a canvas pan. Both add operations are tracked in the shared edit history and are undoable: because mermaid edges have no stable id, undo/redo restore the block's captured before/after source (Ctrl+Z restores the before-source, Ctrl+Y the after-source) through `POST /api/mermaid-block-restore`, rather than replaying the add (which would generate a new id). The add endpoints are `POST /api/mermaid-node-add` and `POST /api/mermaid-edge-add` (see [server-api.md](server-api.md)).
- The same toolbar has a **Delete (`🗑`)** button whose action branches on the node selection. With **one or more nodes selected**, clicking `🗑` deletes all selected nodes and **cascades** the removal of every edge incident to any of them, in one write (so single-node delete is: select the node, then `🗑`). With **no node selected**, clicking `🗑` enters a crosshair **delete-pick mode**; clicking an edge (its label, connector line, or hit band) deletes that single edge, while clicking a node or empty background, Escape, or re-clicking `🗑` cancels. Node deletion removes every source line that names the node as a whole token outside label/quoted regions (declaration, `style`/`class`, and cascaded edge lines), removing an entity/class/composite-state `{ … }` body through its matching `}` and never the diagram-type declaration line; a line naming several nodes (a chain or `&` link) is removed wholesale and a node existing only as an edge endpoint goes with that edge (both recoverable via undo). Edge deletion locates the picked edge by the same per-type identity the edge-title editor uses (so the links it refuses — flowchart `&`/chains, state self-loops — are non-deletable) and removes its line. Deletes are snapshot-undoable through the shared restore endpoint exactly like adds (Ctrl+Z restores the deleted node + cascaded edges, or the deleted edge; Ctrl+Y re-deletes); a delete-control or pick pointer-down does not pan, and selection modifiers are inert during delete-pick. The delete endpoints are `POST /api/mermaid-nodes-delete` and `POST /api/mermaid-edge-delete`.

## Mermaid Error Detection and Auto-Repair
- Each Mermaid render container is parse-checked independently before the page renders; valid blocks render unchanged.
- The parse-check and render passes operate only on containers that have not yet been rendered; a container Mermaid has already rendered (it carries Mermaid's `data-processed` marker or contains a rendered `<svg>`) is skipped by both passes. This keeps the passes idempotent — like the zoom/pan and title-edit passes — so an in-app re-render that leaves the rendered diagrams in place (for example re-opening the already-loaded file from the new-files dropdown, where the server returns identical HTML and the `v-html` binding is not re-patched) does not re-read a rendered diagram's injected CSS as diagram source and never surfaces a spurious "No diagram type detected" error.
- A block that fails to parse is sent to the server (`POST /api/mermaid-diagnose`, body `{source}`) which applies a high-confidence repair-rule catalog and returns `{fixed, fixedSource, issues:[{line, ruleId, message}]}`. The server never parses Mermaid; whether a repair resolves the error is confirmed in the browser by re-parsing `fixedSource`.
- Repair-rule catalog (high confidence; a rule fires only when confident): `semicolon-in-sequence-text` — a `;` in a `sequenceDiagram` note/message text after the label colon is a statement separator and is replaced with a comma; `unquoted-specials-in-flowchart-label` — a flowchart rectangle label `ID[...]` that is not already quoted and contains `(`, `)`, `<`, or `>` is wrapped in quotes (embedded `"` written as `#quot;`); `reserved-word-end-as-node-id` — the reserved lowercase word `end` used as a flowchart node id is renamed to `end_` at every node-id occurrence in the block with the visible label preserved (bare → `end_["end"]`, shaped → `end_[Done]`), while the subgraph `end` closer line, `end` inside another id or inside a label, and the already-valid `End`/`END` are left untouched; `period-in-dotted-inline-edge-label` — a flowchart dotted-link inline label `-. text .->` whose text contains a `.` collides with the dotted-link `.` delimiter and fails to parse, so the label is moved into the pipe form (arrowhead preserved): `A -. a.b .-> B` → `A -.->|a.b| B`. A dotted inline label without a `.` (which parses fine), an already pipe-form dotted edge, a plain dotted arrow, and a `-.`/`.->` sequence inside a node shape or quoted label are left untouched (label regions are masked before matching). The `ampersand-in-edge-label` rule is intentionally not implemented: the bundled Mermaid accepts `&` in edge and node labels, so it is not a parse error and there is nothing to repair.
- When a repair re-parses successfully, the corrected source is rendered for that block in memory and an inline `.mermaid-repair-box` (kind `fixed`) is shown next to the diagram, listing each issue as `line N: <message>` with a Quick Fix button. Rendering never writes to disk.
- Clicking Quick Fix calls `POST /api/mermaid-fix` (body `{path, line, index}`), which locates the block via the existing block locator, re-derives the repair from the on-disk source (it does not trust client-sent text), writes it back, and the browser reloads so the now-valid diagram renders and the box clears.
- A block with no available repair is not rendered by Mermaid (its `mermaid` class is removed so Mermaid skips it and injects no raw error SVG; the placeholder is hidden). An inline `.mermaid-repair-box` (kind `unfixable`) shows the diagnosed issue lines, or Mermaid's own parse reason when no rule matched, with no Quick Fix button.
- Prepared blocks are rendered one container at a time. A block that passes the parse check but still throws while Mermaid renders it is contained to its own diagram: it is marked unrendered (its `mermaid` class removed so no raw error SVG remains) and shown as the same `unfixable` inline `.mermaid-repair-box` carrying Mermaid's render reason, without a Quick Fix button. A single failing block does not abort rendering, zoom/pan, or title-edit binding for the other diagrams, and the render-time failure is not surfaced through the page-level error banner; because the box lives in the rendered content, a later reload after the source is fixed rebuilds the content and the box disappears on its own.

## Diagram Canvas Zoom and Pan
- Rendered Mermaid diagram canvases and rendered maxGraph XML diagram canvases support mouse-wheel zoom and drag-to-pan through a shared browser zoom/pan controller.
- Wheel zoom requires the Ctrl or Cmd (`metaKey`) modifier; a plain wheel without the modifier keeps scrolling the page, and trackpad pinch gestures (reported by the browser as Ctrl+wheel) zoom as well.
- Wheel zoom zooms toward the cursor so the diagram content point under the pointer stays under the pointer, and the zoom scale is clamped between a minimum factor of `0.2` and a maximum factor of `8`.
- Dragging on an empty area of a diagram canvas pans the diagram within its frame. On a maxGraph canvas, drags that start on an entity box, an entity or edge title editor, an edge label, an edge connector line or its transparent hit band, or the Add control keep their existing behavior and do not start a pan; only empty-background drags pan. (A pointer-down on the Add `+` button must not start a pan, or it would steal the click that opens the menu.)
- While a maxGraph entity-box or edge title is being edited inline, a single click on an empty area of the canvas commits the open editor: the click blurs the editor so its save-on-blur runs and does not start a pan. A later click on empty background pans normally. Pressing Escape while the editor is open also commits it (same as blurring) and is consumed by the editor, so it does not bubble to the canvas selection-clear or add-edge/delete pick-mode-cancel Escape handlers.
- Double-clicking an empty area of a diagram canvas resets that diagram to the default view (scale 1, no pan offset).
- The diagram canvas (clip box) height tracks the scaled diagram height: at scale 1 it matches the natural diagram height, and as the reader zooms in and the diagram grows the canvas grows with it. The canvas height is capped at the current view window height (`window.innerHeight`); when the scaled diagram is taller than the view window the canvas stops growing at the window height and the rest stays reachable by drag-to-pan and zoom. Zooming back out shrinks the canvas back toward the natural diagram height. The maxGraph canvas keeps its padding and border framing at scale 1, so this resize introduces no scale-1 framing regression.
- Zoom and pan are view-only and are never written back to the markdown file. The view state for each diagram persists within the browser session (keyed by diagram order) so timed auto refresh and in-app markdown re-render preserve the current zoom and pan; a full browser page reload resets every diagram to the default view.

## maxGraph XML Rendering
- Fenced code blocks whose info string is `maxgraph`, `mxgraph`, `maxgraphcolor`, or `maxgraphcolorall` are converted into maxGraph-compatible diagram containers. Info string matching is case-insensitive.
- Supported source is `mxGraphModel` XML, the same model shape used for maxGraph's mxGraph import path, or draw.io `mxfile` XML containing an `mxGraphModel`.
- maxGraph XML diagram source is escaped into a template inside the render container before client-side rendering.
- The browser UI renders maxGraph XML containers after each successful markdown render using the local SVG renderer in app static JavaScript and CSS, without fetching internet/CDN assets and without loading upstream `@maxgraph/core` adapter code.
- `maxgraph` and `mxgraph` containers use normal maxGraph style mode: style `fontSize` applies to node and edge labels, and rectangle vertex cells plus orthogonal edge bends always render rounded as if `rounded=1`; source `rounded` values are ignored in this mode. `maxgraphcolor` containers use color maxGraph style mode: `strokeColor` applies to node shape stroke plus edge stroke and visible arrow marker color, `fontColor` applies to node and edge labels, `fontSize` applies to node and edge labels, and rectangle vertex cells plus orthogonal edge bends always render rounded as if `rounded=1`; source `rounded` values and `fillColor` are not supported in this mode. `maxgraphcolorall` containers use color-all maxGraph style mode: `fillColor` applies to node shape fill, `strokeColor` applies to node shape stroke plus edge stroke and visible arrow marker color, `fontColor` applies to node and edge labels, `labelBackgroundColor` applies to node and edge label background fills, `fontSize` applies to node and edge labels, and `rounded` applies to rectangle vertex cells and orthogonal edge bends. Straight edges are not visually changed by `rounded`, and invalid `fontSize` or unsupported/mode-gated style values fall back to CSS defaults.
- maxGraph XML vertex cells render as rectangles by default (rounded per the active style mode). A cell whose style requests an ellipse (`shape=ellipse` or a bare `ellipse` style key) renders as an `<ellipse>`, and a cell requesting a rhombus (`shape=rhombus` or a bare `rhombus` style key) renders as a diamond `<polygon>`; unrecognized shape hints fall back to a rectangle. All vertex shapes carry the `maxgraph-node-shape` class with the mode-resolved fill and stroke colors.
- maxGraph XML edge styles `startArrow` and `endArrow` independently control source and target SVG markers on straight and orthogonal edges. Supported values are `none`, `classic`, `classicThin`, `block`, `blockThin`, `open`, `openThin`, `oval`, `diamond`, and `diamondThin`; `none` omits that side's marker, `open` and `openThin` render unfilled stroked markers, `oval` renders a circle/oval marker, and each `Thin` value renders a narrower version of its base shape. Missing or unsupported `startArrow` keeps no source marker. Missing or unsupported `endArrow` keeps the default classic target marker.
- maxGraph XML edges whose style includes `edgeStyle=orthogonalEdgeStyle` render as right-angled connector paths; maxGraph XML edges without that style render as straight connector lines.
- maxGraph XML rendering ignores imported fixed link position metadata from the source diagram, including edge geometry points and `exitX`/`exitY` or `entryX`/`entryY` style coordinates. Rendered source and target attachment sides, attachment points, and orthogonal paths are selected only by the local routing rules below.
- maxGraph XML orthogonal edge paths approach their selected source and target sides perpendicularly so arrowheads are not hidden by node shapes.
- maxGraph XML edges that would otherwise attach to the same rendered entity side are distributed to distinct attachment points along that side; all incoming and outgoing points on that side share one spacing group. When the usable side span permits it and higher-priority node avoidance, link conflict, endpoint-clearance, and route-scoring rules are not worsened, adjacent points use even clearance of at least two arrow widths and the group is centered on the side middle. The router may switch same-side point order across incoming and outgoing links when the alternate order improves the selected routes without violating spacing.
- maxGraph XML orthogonal edge routing shifts internal route lanes when needed so horizontal and vertical connector segments do not overlap or sit closer than the required parallel-segment visual clearance from other collinear orthogonal connector segments.
- maxGraph XML orthogonal edge routing prioritizes multi-edge source fanout bundles before shorter feedback or loopback links when practical, so a source with many outgoing connectors can keep a clean low-bend corridor while later links still follow node avoidance, link-conflict avoidance, and endpoint-clearance rules. Incoming links to high-fanout entities may be routed before that entity's outgoing fanout bundle when doing so preserves lower crossings, non-overlapping segments, entity-box clearance, endpoint clearance, or fewer bends.
- When connected source and target nodes overlap vertically or horizontally and compatible facing sides can be joined by one straight orthogonal segment without violating node avoidance, link conflict, or endpoint-clearance rules, maxGraph XML orthogonal edge routing chooses that straight segment instead of adding bends.
- maxGraph XML orthogonal edge routing chooses from direct and low-bend route candidates, avoids non-endpoint entity nodes when an alternate route is available, avoids partial or full overlap with already-routed collinear links when a non-overlapping route is available, avoids crossings with already-routed links when a non-crossing route is available, and then prefers the candidate with the fewest right-angle turns. When crossing counts tie, the router prefers fewer bends, the source side facing the target row or column, centered attachment points, even same-side attachment clearance, and the shorter path.
- maxGraph XML orthogonal edge routing avoids routes whose first or last endpoint segment is so short that the adjacent perpendicular segment appears to connect to the side of an arrowhead.
- For maxGraph XML orthogonal edges, route selection may evaluate alternate source/target sides, shifted attachment points along those sides, and alternate same-side ordering of existing connection points to reduce route conflicts; when higher-priority route rules tie, attachment points stay closest to the middle of their selected side and same-side groups keep even clearance. Imported fixed link positions never prevent side-pair optimization, while same-side spacing may move a rendered point along that selected side to prevent connection-point overlap, keep a same-side group centered and evenly spaced when practical, keep a preferred low-bend side usable when another incoming or outgoing port already occupies the centered point, or switch same-side port order when that produces the better route.
- maxGraph XML edge labels are rendered as horizontal text on a rendered edge segment. The renderer prefers a horizontal segment when the one-line label width fits within that segment and the best placement on that segment has practical clearance from cells, connector segments, and existing text; if multiple horizontal segments qualify, it chooses the one with the best placement clearance and then the longer segment. When no horizontal segment can hold the label with practical clearance, the renderer falls back to the longest rendered edge segment. The renderer prefers a single line and may wrap to two or three lines only when that fits the available space better; wrapped labels choose word-break positions that keep visible line widths similar and avoid a very short final line when another valid layout fits the same label width cap. Labels attached to horizontal segments are placed above or below the segment without covering the connector; if the centered placement overlaps cells, connector segments, or existing text, the renderer tries shifted positions left and right along the same segment and chooses the placement with the least overlap. Labels attached to vertical segments are placed on the left or right when that side has room, with horizontal label padding and margin set to 0 so the visible title text's inner edge sticks close to the vertical segment and leaves only 4 points of clearance. If the initial side placement overlaps or sits close to horizontal connector segments, entity boxes, other arrows or connector segments, cells, connector segments, or existing text, the renderer tries left/right side placements and shifted positions up and down along the same segment, then chooses the placement that keeps practical clearance from nearby diagram elements while still staying farthest from nearby horizontal segments and minimizing overlap. If both vertical sides remain worse than crossing the segment, the label may cross the vertical segment. Placement should avoid cells, other connector segments, and other labels or node text unless no practical non-overlapping placement exists. The SVG canvas and viewBox are sized from node bounds, routed connector segment bounds, and final edge-label text block bounds so routes and labels placed outside the node area are not clipped.
- maxGraph XML edge titles are editable by double-clicking the rendered edge title (its label) **or by double-clicking the edge connector line / its transparent hit band**. The line path lets an **untitled** edge — which renders no label to double-click — be titled from the canvas: a titled edge reuses its existing label box (identical to double-clicking the label), while an untitled edge opens a blank editor anchored at the double-click point. Either way the editor opens at a minimum editing area of **150 wide × 50 high** (SVG user-space units): a titled edge's label box is floored up to that size, and an untitled edge's blank editor uses 150×50 as its default box so it stays centred on the click point. A double-click on the line stops propagation so it does not reset the canvas zoom/pan, and the line path is inert while the canvas is in delete mode or add-edge pick mode (those modes claim the click). The editor is a textarea sized for 3 text lines, Enter inserts line breaks, blur saves changed text back to the matching edge cell's `value` attribute in the original fenced XML block (inserting a `value` attribute when the edge had none), unchanged edits close without a save request, and saved line breaks render as separate SVG text lines in the edge label. An edit that clears the title to the empty string is saved as an empty `value` (`value=""`), leaving the edge unlabeled; the edge stays re-editable by double-clicking its connector line / hit band, so no placeholder label is forced onto it. The inline editor is removed when the save succeeds, not only as a side effect of the re-render, so the editor box closes (and the edge's transient saving state clears) even on a save whose reload renders identical HTML and does not re-render the canvas. A successful changed edge-title save is recorded in the current browser-session maxGraph edit history.
- Rendered maxGraph XML entity boxes can be dragged to a new canvas location. While an entity box is being dragged, the browser checks the latest dragged position every 0.1 seconds and re-renders the current browser canvas from an in-memory diagram copy only when no previous in-drag preview render is still in progress and that position differs from the position used for the previous completed in-drag preview render; a timer tick that finds a preview render still in progress skips starting another render. This refreshes routes and labels during the drag without saving the markdown file while preserving drop as the only persistence point. Dropping a box writes the vertex cell's updated `mxGeometry x` and `y` attributes back to the original fenced XML block in the markdown file, preserving any draw.io `mxfile` wrapper, invalidates the saved render, and re-renders the diagram from the updated markdown.
- Multiple rendered maxGraph entity boxes can be **selected** and then moved together. Selection is nodes only (edges are not selectable) and is additive: while the **Shift** key is held the canvas shows a crosshair and a pointer drag draws a rubber-band selection rectangle (instead of panning or moving a node), and on release every node whose box intersects the rectangle is **added** to the selection — repeated Shift-drags accumulate nodes across separate regions. While the **Ctrl** (or Cmd) key is held, a left click on a node toggles that node in the selection (no drag, no pan), and the canvas shows the same crosshair cursor as Shift; Ctrl+wheel still zooms. The selection persists across plain background clicks (which still pan); pressing **Escape** clears it; and starting a plain single-node drag on a node that is not part of the selection clears the selection and moves just that node. Selection is per render and resets after a save/reload, with one exception: a group-move drop restores the just-moved nodes as selected on the reload it triggers (see the next bullet). Any other re-render (navigation, single-node drag, add/delete, auto refresh) still resets the selection.
- When two or more nodes are selected, a plain (no-modifier) drag that starts on any **selected** node moves all selected nodes together, translating them live with the pointer. Any edge whose **both** endpoints are in the selection moves rigidly with the group during the drag — its connector, arrowheads, and label translate by the same offset (exact, since both endpoints shift equally) — while an edge with only one selected endpoint stays in place during the drag and re-routes after the drop reload. On drop, every moved node's new `mxGeometry x`/`y` is written back to the same fenced XML block in **one atomic file write** through `POST /api/maxgraph-nodes`; if any selected vertex cannot be located, none are written. A group drag with no net movement persists nothing. The whole group move is recorded as a single browser-session edit-history entry, so one Ctrl+Z reverts all the moved nodes and one Ctrl+Y reapplies them. After the drop reload, the moved nodes **stay selected** (highlighted): the moved set is recorded just before the reload and re-applied on the next render of that diagram, so the user keeps the same set selected and can immediately move it again. A failed save (no reload) leaves the pending restore unused.
- Rendered maxGraph XML entity box titles can be edited inline. Double-clicking an entity box or its title opens a multiline textarea editor inside that box, inset by 2 points on each side so its width and height equal the cell box size minus 4 points, floored at a minimum editing area of **150 wide × 50 high** (SVG user-space units) so a small entity box still gets a usable editor. Pressing Enter inside the textarea inserts a newline rather than saving or closing. Saved title line breaks render as separate SVG text lines inside the entity box, and automatic title wrapping uses the available entity-box title width instead of a fixed short character count. When the editor loses focus with changed text, the browser writes the new title to the matching vertex cell's `value` attribute in the original fenced XML block, preserving any draw.io `mxfile` wrapper, invalidates the saved render, re-renders the diagram from the updated markdown, and records the changed title in the current browser-session maxGraph edit history. An edit that clears the title to the empty string is saved as `_` (a placeholder) rather than an empty `value`. The inline editor is removed when the save succeeds, not only as a side effect of the re-render, so a save whose persisted value equals the currently rendered value — clearing an already-`_` title, which the server normalizes back to `_` and which therefore yields an identical reload that does not re-render the canvas — still closes the editor box and clears the node's transient saving state. If focus leaves while the title text is unchanged, the editor closes locally without calling the save API, refreshing the markdown render, or recording history.
- A persisted maxGraph entity-box title change also auto-resizes that vertex to accommodate the new title: the server rewrites the cell's `mxGeometry` `height` to a fixed **60** and `width` to fit the title, clamped to the inclusive range **[90, 360]**. The width fits with as few wraps as possible (the box is widened up to the 360 cap so the title stays on the fewest lines; only a title too wide for the cap wraps). The width is derived from the title text alone (the widest newline-separated line at a 7px-per-character, 20px-horizontal-padding metric), so undo/redo — which replays the previous/next title through the same endpoint — restores the size matching each title. A cell with no `mxGeometry` is left at its title-only update. As a consequence, a hand-authored non-fitting width is replaced by the fitted width the first time its title is edited.
- When rendering an entity-box title, a single substring/word that cannot be broken at whitespace and whose rendered width exceeds the box content width is hard-wrapped into chunks no wider than the content width (at the 360 cap, the max content width is 340) **at render time only** — the stored `value` attribute text is not changed. The renderer renders all wrapped/hard-wrapped lines without truncating to a fixed line count or appending an ellipsis.
- The rendered entity-box title (its text and any label background) is clipped to the node's geometry box via a per-node SVG `clipPath`, so any title that still extends past the border — because a wide-glyph word exceeds the character-width estimate or the line count exceeds the fixed 60 height — is hidden at the node border rather than overflowing outside it. Only the label is clipped, not the shape, so the border stroke is not cut; a title that already fits within the auto-sized box is not clipped.
- Successful maxGraph XML entity-box moves (single and multi-node group moves), entity-title changes, edge-title changes, node/edge additions, and node/edge deletions are tracked in browser-session edit history with a shared 50-step limit. Ctrl+Z undoes the latest saved maxGraph edit by writing the reverse change back to the markdown file and re-rendering (an undone group move restores every moved node's previous position in one step; an undone addition is deleted; an undone deletion restores the diagram block to the snapshot captured before the delete, bringing back a node together with all its cascaded edges); Ctrl+Y reapplies the next undone edit (a redone group move re-applies all the new positions; a re-added node/edge keeps its original id, title, and geometry; a redone deletion re-runs the delete). A new successful maxGraph edit clears redo history. These shortcuts are ignored while focus is in a text-editing control.
- Each rendered maxGraph canvas shows a row of icon buttons pinned to the top-right corner, above the canvas and outside the zoom/pan transform (so they stay put while the diagram is zoomed or panned): an **Add Node** (`+`) button, an **Add Edge** (`→`) button, and the **Delete** button. There is no dropdown menu — each button triggers its action directly with one click.
- Clicking the **Add Node** (`+`) button inserts a new vertex titled `New` into the source XML and re-renders. The node is placed at the 3/4 top-right of the **current view**: its center is at 75% of the visible canvas width and near the top, mapped from screen to diagram coordinates through the live SVG transform, so it respects the current zoom/pan. It uses a default rectangle style and a default 120×60 size; the title is then editable through the existing entity-title editor.
- Clicking the **Add Edge** (`→`) button enters an edge-pick mode: the canvas shows a picking cursor and the user clicks two nodes in turn — the first is the edge source, the second the target — and a new edge titled `New` is inserted from source to target using the right-angle (orthogonal) connector style (`edgeStyle=orthogonalEdgeStyle`), so it renders with 90° segments. The first picked node is highlighted while the second is awaited. While edge-pick mode is active, node drag, title editing, and canvas pan are suppressed so a click only picks an endpoint. The Add Edge button toggles the mode: clicking it again cancels edge-pick. Pressing Escape, clicking the background, clicking the Add Edge button again, or picking the same node twice (no self-loop) cancels the mode without creating an edge.
- A new node/edge is written into the same maxGraph code block as a new `<mxCell>` under `<root>`, leaving the rest of the block intact. If the block body is empty or whitespace only, adding a node first scaffolds a valid `mxGraphModel` (with `id="0"`/`id="1"` layer cells) holding that vertex; an edge cannot be added first, since an empty block has no source/target vertices. Its id is generated in the browser to be unique within the block (so undo→redo is stable); the server rejects a duplicate id, an unknown source/target vertex, or a self-loop.
- Each rendered maxGraph canvas also shows a **Delete** button pinned to the top-right corner **beside the Add Node (`+`) and Add Edge (`→`) buttons**, above the canvas and outside the zoom/pan transform, styled to match them. Clicking it enters a **delete mode**: the next click on a rendered node removes that node, and the next click on a rendered edge — its connector line or its label — removes that edge. The edge connector line carries the edge id, so an edge can be selected by clicking the line itself (an untitled edge has no label); because the thin connector is hard to hit, each edge also has a wider transparent hit overlay — a normal-use pointer target (it also receives the double-click-to-edit-title interaction) that shows the delete crosshair while delete mode is active. The deletion is persisted to the source XML block and the diagram re-renders; delete mode then ends.
- **Deleting a node cascades to its edges**: every edge whose `source` or `target` is that node is removed in the same operation, so no dangling edge is left in the XML. Deleting an edge removes only that edge.
- **Clicking the Delete button while one or more nodes are selected deletes the whole selection at once** instead of entering single-pick mode: every selected node is removed together with all edges connected to any selected node (the same `source`/`target` cascade as a single node delete; an edge whose both endpoints are selected is removed once). The whole group delete is persisted in one atomic write through `POST /api/maxgraph-nodes-delete` (if any selected vertex cannot be located, none are removed) and recorded as a single browser-session edit-history entry, so one Ctrl+Z restores every deleted node and its cascaded edges (from the pre-delete block snapshot) and one Ctrl+Y re-runs the group delete. When nothing is selected the Delete button keeps its single-pick toggle behavior. Edges are not independently selectable, so a bare edge is never a group-delete target.
- Delete mode is entered only by clicking the Delete button and is mutually exclusive with the Add-edge pick mode (entering one cancels the other). Pressing Escape, clicking empty canvas background, or clicking the Delete button again cancels delete mode without removing anything. While delete mode is active, node drag, title editing, and canvas pan are suppressed so a click only selects a delete target, and the canvas and nodes show a crosshair cursor (matching add-edge mode).
- A delete is recorded in the browser-session maxGraph edit history. Ctrl+Z undoes a delete by restoring the whole diagram block to the snapshot captured just before the delete (a cascade delete restores the node and all its connected edges together, with their original styles, geometry, and labels), and Ctrl+Y redoes the delete. The browser captures the block XML before the delete and, on undo, writes it back through `POST /api/maxgraph-block-restore`.
- The maxGraph diagram container clips its content (`overflow: hidden`) instead of exposing a horizontal scrollbar; the empty-background drag-to-pan and Ctrl+wheel zoom described under Diagram Canvas Zoom and Pan provide navigation of content outside the frame. A pan versus an entity-box move is distinguished by the pointer-down target, so dragging an entity box still moves the box while dragging empty canvas background pans the view.
- Other rendered maxGraph XML content remains non-editable and maxGraph XML fences are not exposed through the fenced code block write-back API.
- A maxGraph block that is a valid `mxGraphModel` (or a draw.io `mxfile` containing one) with **no vertex cells**, and a maxGraph fenced block whose body is **empty or whitespace only**, both render as an empty canvas (a finite, default-sized SVG) rather than an error. The empty canvas still shows the Add (`+`) and Delete controls, so the first node/edge can be added; adding the first node to an empty-bodied block scaffolds a valid `mxGraphModel` (with the standard `id="0"`/`id="1"` layer cells) containing that vertex.
- If a maxGraph XML block is invalid XML, or parses to a root that is neither an `mxGraphModel` nor a draw.io `mxfile` containing an `mxGraphModel`, the browser shows an inline diagram error instead of throwing an uncaught JavaScript error.
- Raw maxGraph XML outside a `maxgraph`, `mxgraph`, `maxgraphcolor`, or `maxgraphcolorall` fence is not auto-detected.

## Invariants & design constraints
_Maintainer rules the behaviors above depend on — the coupling a future change must not break. Migrated from working memory 2026-07-02; see change package `../../changes/2026-07-02-memory-invariants-backfill/`._

- **Post-render passes must be idempotent.** The browser re-runs every post-render pass (Prism, maxGraph render, Mermaid parse-check/render, zoom/pan, title-edit binding, selection binding) after each render — including in-app no-op reloads, where the server returns identical HTML and Vue does **not** re-patch the `v-html` binding, so the already-rendered DOM stays in place. Every pass must no-op on already-processed elements (skip a Mermaid container carrying `data-processed`/a rendered `<svg>`, a viewport that already has `.mermaid-viewport`, an already-bound node) and must **never re-read rendered output as source** (a rendered diagram's injected CSS is not diagram source). Any new post-render pass must follow the same rule. Change package: `../../changes/2026-06-21-mermaid-skip-rendered-on-reload/`.
- **Inline editors tear down on save success, not on the re-render.** An inline title editor (maxGraph/mermaid `foreignObject` textarea + transient `*-saving` class) must close and clear its own state on the awaited save success. It cannot rely on the post-save re-render to remove it, because a normalize-back save (e.g. clearing an already-`_` node title, which the server re-normalizes to `_`) persists the value already rendered → identical HTML → no re-render → the editor would leak open. Closing on success is safe either way (on a real change the old nodes are already detached). Change package: `../../changes/2026-06-23-maxgraph-title-editor-closes-on-save/`.
- **Mermaid edge identity is a DOM ordinal coupled to the backend regex.** er/class/state edge write-back locates the edge by ordinal: the browser sends the i-th rendered edge and the backend rewrites the i-th source line matching its per-type relationship regex. The two must enumerate the **same set of edges** — including label-less relationships (mermaid renders an edgeLabel group for every edge regardless of label), so the relationship regexes are colon/label-optional. A grammar change that makes the regex match only labelled edges silently desyncs the ordinal and rewrites the wrong edge. Change packages: `../../changes/2026-06-04-mermaid-edge-title-editing/`, `../../changes/2026-06-30-mermaid-edge-line-title-and-empty-clear/`.
- **Mermaid structural edits undo via block-source snapshots, not delete-by-id.** Mermaid has no live model and its edges have no stable id, so add/delete node/edge round-trips through source + reload, and undo/redo restore the block's captured before/after source through `POST /api/mermaid-block-restore` (not a reverse-by-id like maxGraph). New-node ids are server-generated (`New_<n>`) because the client sees only rendered ids. Change package: `../../changes/2026-06-30-mermaid-canvas-graph-editing/`.
- **Edge clickability uses a transparent hit band, never a wider stroke.** A rendered edge is made double-click/delete targetable by laying a transparent `*-edge-hit` overlay (same geometry, carrying the edge id) over the thin connector — not by widening the visible stroke, because arrow markers use `markerUnits: strokeWidth` and a wider stroke balloons the arrowheads. The visible path also carries the id so an untitled (label-less) edge stays selectable.
- **Mermaid mode cursors target the viewport, not the outer container.** The mermaid canvas is `.mermaid > .mermaid-viewport(cursor: grab) > .mermaid-pan > svg`. A mode cursor (marquee / add-edge / delete) must be set on `.mermaid-viewport` (e.g. `.mermaid.mermaid-marquee-ready .mermaid-viewport`), because the viewport's own explicit `cursor: grab` overrides a crosshair merely *inherited* from the outer `.mermaid`. (maxGraph differs: its `.maxgraph-diagram` element is itself the grab surface.)
