# Browser UI, Typography & Navigation

_[← Application Features index](../application-features.md)._ The Vue/Quasar viewer chrome: toolbar controls (navigation, file/folder dropdown, auto-refresh, theme, font-scale, the notification bell), error banner, rendered-content typography and table styling, URL/history navigation, and the in-preview content search. The dropdown metadata and the bell's backend behavior are in [file-navigation.md](file-navigation.md).

## Browser UI
The UI includes:
- In-app navigation controls in a left-aligned toolbar group (`viewer-nav`): a Home button (icon `home`, accessible name `Home`) pinned as the first control, which navigates to the configured content root; the file/folder dropdown (described next); then Back and Forward buttons (icons `arrow_back`/`arrow_forward`, accessible names `Go back`/`Go forward`). Back and Forward drive `window.history.back()`/`window.history.forward()` through the existing `popstate` reload and are each disabled at their history boundary (Back at the first session entry, Forward at the most recent entry). The same history back/forward is also bound to the `Alt+Left` and `Alt+Right` keyboard shortcuts (no other modifier; ignored when Ctrl/Cmd/Shift is also held), primarily so the VS Code preview iframe — which lacks the browser's own history keys — still has keyboard history navigation.
- File/folder dropdown pinned to the left edge of the page toolbar, immediately after the Home button, listing a maximum 3-level expanded tree of `.md` files and markdown-bearing folders from the current folder, including `..` parent navigation outside the content root. The control has no visible field label, but keeps an accessible name of `Current folder`. Its normal width follows the selected file/folder label with minimum and maximum bounds so short names do not create a wide empty control and long names do not crowd the right-edge toolbar controls. The toolbar's middle area absorbs spare horizontal space, and narrow layouts may wrap toolbar groups onto separate rows while preserving left alignment for the file/folder dropdown.
- File/folder dropdown folder rows can be collapsed and expanded. Each folder that has at least one descendant option in the current list shows an inline chevron toggle (`chevron_right` when collapsed, `keyboard_arrow_down` when expanded); `..` parent rows and `.md` file rows show no toggle. Collapsing a folder hides all of its descendant rows (every following deeper-depth option until depth returns to that folder's level or shallower) and expanding it restores them, with nested collapse state preserved underneath a collapsed ancestor. Folders are expanded by default. On a folder row, the chevron toggle, the folder icon, and the empty indentation band to the left of the chevron (between the dropdown's left edge and the chevron) all collapse/expand the folder; none of them selects the folder, navigates, nor closes the dropdown. Only clicking the folder name (label) navigates into that folder. `.md` file and `..` parent rows still navigate when clicked anywhere on the row, including their leading indentation band. Collapse state is keyed by folder relative path and kept in memory for the browser session, so it survives dropdown re-opens and in-app navigation but resets to all-expanded on a full page reload. Collapse/expand is view-only and is never written back to the markdown files or backend. Collapsing or expanding a folder (including nested subfolders, via the chevron or the folder icon) preserves the dropdown's current scroll position pixel-precisely: the toggled folder row's viewport offset inside the open menu is captured before the option list re-renders, and afterward the row is re-measured and the menu's scroll nudged so that row returns to the same on-screen offset — re-applied on the menu's scroll event and across animation frames for a short window so it stays exact even in large virtualized lists where QSelect's content-height re-estimation would otherwise leave a small residual jump (and where Quasar's QMenu would jump the scroll to the selected option). If the toggled row is outside the rendered virtual slice, the restore falls back to the row's pre-toggle scroll offset.
- Toolbar dropdown popup height. The file/folder dropdown popup and the notification bell dropdown may each extend to at most 90% of the viewport height (`max-height: 90vh`, overriding Quasar's 65vh menu default) so tall windows show more rows before scrolling; Quasar's runtime menu positioning may still shrink an open popup further to fit the space actually available between its toolbar anchor and the viewport edge. Other toolbar menus (auto refresh, theme) keep the Quasar default.
- File name search control. A `search`-icon button (accessible name `Search files by name`) sits in the right-edge control group (`viewer-controls`) as its **first** control, immediately to the left of the notification bell. It opens a dropdown popup (anchored bottom-right/top-right, like the bell) containing a single-line input (autofocused on open), a results list, and a footer with previous/next page navigation shown only when there is more than one page. The user types a name; a search runs **0.7 s after the last keystroke** (debounced) and only when the query — after normalization (lowercase, non-alphanumerics stripped; see [file-navigation.md](file-navigation.md)) — is at least **3** characters. Shorter or empty/whitespace/punctuation-only input shows the hint `Type at least 3 characters` and issues no request, cancelling any pending search and clearing results; a new query resets to page 1. Results are fetched from `GET /api/search-files` (backend behavior in [file-navigation.md](file-navigation.md)), 10 per page, and reuse the notification item style (`.viewer-new-file-*`): each row shows the filename, its parent folder, and the file's activity date/time, with **no** unviewed-bold weighting and **no** needs-review dot. A query that matches nothing (≥3 chars) shows an italic `No files match.` row; when the backend caps the match set at 500 the popup notes it. Clicking a `.md` result opens it in the viewer (`loadFile`) and closes the popup; clicking any other result (including images) opens `/api/file/{path}` in a new browser tab. The input text and its results persist while the popup is reopened within the session. This is separate from the In-Preview Content Search below.
- No separate page toolbar title for the current markdown file name; the selected file/folder control and browser URL provide the current location.
- The browser window/tab title (the HTML `document.title`, distinct from any in-page toolbar element) tracks the current file as `MD Activator - <simple name>`, where `<simple name>` is the viewed file's basename including extension (for example `docs/guide.md` shows `MD Activator - guide.md`). With no file resolved (the content-root entry before a file loads) the title is the plain prefix `MD Activator` with no trailing separator. The title updates on every real render — initial load, file/folder dropdown selection, rendered local-link navigation, Home/Back/Forward, `popstate`, and direct-URL navigation — and is left unchanged by a `no-change` auto-refresh. When the viewer runs embedded in another browsing context (the VS Code preview iframe), it also posts the current simple name to its parent frame as a `{ type: 'md-activator:title', simpleName }` message so the host can update its own tab title; in a top-level browser tab it sets `document.title` only and posts nothing. See Launchers & Packaging for how the VS Code extension consumes this to update the preview panel tab.
- Auto refresh dropdown is grouped with the theme dropdown at the toolbar's right edge and appears before the theme dropdown. The group remains right-aligned when narrow layouts wrap toolbar groups onto separate rows. The control has no visible field label or dropdown arrow, but keeps an accessible name of `Auto refresh`.
- Auto refresh is initiated by the browser UI and refreshes the currently selected markdown render without requiring backend scheduling.
- Auto refresh must not refresh the file/folder dropdown structure; it preserves the current dropdown options while refreshing rendered markdown content.
- Opening the file/folder dropdown requests file/folder metadata for the current path before the user selects an item. The response updates dropdown options, but the server may reuse a folder metadata cache entry that is still fresh under the 5-second rule instead of forcing an immediate disk rescan.
- Auto refresh defaults to every 3 seconds.
- Auto refresh interval options are 1, 2, 3, 5, 10, 20, 30, and 45 seconds, plus 1, 2, 3, 5, 10, 20, 30, 45, and 60 minutes.
- Auto refresh timing is aligned to local-time interval boundaries measured from local 12:00 AM. For example, a 10-second interval refreshes on local-day offsets divisible by 10 seconds.
- Auto refresh keeps the currently rendered markdown visible while the next render is fetched and prepared, then replaces the content after the new render payload is available so normal refreshes do not flash to an empty or loading state.
- Auto refresh sends the current `renderVersion` for the open markdown file. When the server returns `{"status": "no-change"}`, the browser treats the request as a successful refresh without changing rendered HTML, rerunning Prism, Mermaid, or maxGraph XML rendering, changing the URL, or touching dropdown options.
- Theme dropdown is grouped with the auto refresh dropdown at the toolbar's right edge and appears after the auto refresh dropdown with `System`, `Light`, and `Dark` options. The control has no visible field label or dropdown arrow, but keeps an accessible name of `Theme`. The selected theme persists per browser in `localStorage` (`mdViewerTheme`) and is restored on load, falling back to `System` when storage is unavailable. While `System` is selected, the viewer follows live OS light/dark changes and re-applies the effective theme without a reload; `Light` and `Dark` pin the theme regardless of the OS setting.
- Notification icon. A single bell button (icon `notifications`, accessible name `New markdown files`) sits at the start of the toolbar's right-edge control group. Its floating badge shows `attentionCount` (files needing review plus unviewed non-review new files), and its dropdown is one continuous list: files that still contain an unchecked `[ ] Confirm` marker are listed first — each row prefixed by a small yellow circle marking it as a "needs review" item — followed by the recently-created new `.md` files, with a single paging control over the combined list. A footer row beneath the list (shown whenever the list has files) carries a borderless **Mark all viewed** button that marks every file in the list viewed in one click, beside the paging controls; the button has a tooltip clarifying that clarification (yellow-dot) files keep their badge until their Confirm box is ticked. There is no separate `rate_review` bell. See New Markdown File Notifications (in `file-navigation.md`) for scope, ordering, polling, viewed-state, mark-all-viewed, and self-clearing (confirm-to-dismiss) behavior.
- Rendered-content font size controls. Two icon buttons sit at the left of the toolbar's right-edge control group, immediately before the auto refresh dropdown: a decrease (smaller) button then an increase (bigger) button, using the `text_decrease` and `text_increase` icons with accessible names `Decrease font size` and `Increase font size`. Each press steps a content font scale by 0.1, clamped to a 0.5–3.0 range and saturating at the bounds; the default scale is 1.0 (unscaled). The scale multiplies the rendered markdown body's base text and heading sizes through the `--content-font-scale` CSS variable, so a scale of 1.0 preserves the current sizes exactly while larger/smaller scales grow or shrink the whole rendered content proportionally. The scale persists per browser in `localStorage` (`mdViewerFontScale`) and is restored on load, falling back to 1.0 when storage is unavailable. The control is view-only: it restyles the already-rendered body without re-rendering and is never written back to the markdown file or backend.
- Local browser CSS and JavaScript URLs include a static asset version token derived from the served asset files so normal browser profiles do not keep stale toolbar code after local edits.
- Browser runtime libraries load from local server paths: Vue, Quasar CSS/JS, Quasar Material Icons, Prism, Mermaid, app CSS, app JavaScript, and local maxGraph CSS/JS must be served from `/assets/...` or `/static/...` and must not require internet/CDN access. maxGraph-compatible XML route selection and SVG rendering remain implemented in local app JavaScript, with no upstream maxGraph adapter bundle.
- Error banner. The browser UI error banner distinguishes a transient connectivity error from a sticky operation error. A transient error is a failed fetch — a failed `/api/render` auto-refresh or file-option refresh (for example the native `Failed to fetch` while the server is briefly unreachable) — and is cleared as soon as a later fetch succeeds: the next successful render, `no-change` refresh, or file-option refresh removes it without any navigation, so a recovered connection hides the message on its own. A sticky error is a write-back/operation failure — checkbox or button-option write-back, non-diagram code-block write-back, maxGraph/mermaid title or node-position write-back, and the missing-URL-file message — and is not wiped by a subsequent successful auto-refresh; it remains visible across same-page operations and is cleared only when the viewer successfully renders a different markdown page (a render whose resolved path differs from the one currently shown): in-app file or folder dropdown selection, rendered local-link clicks, Home/Back/Forward, browser `popstate`, and direct-URL navigation that resolves to a different path. A later error replaces the visible message, and a navigation to another page that itself fails surfaces the new error rather than leaving the previous page's message.
- Rendered markdown body.
- Rendered checkbox changes persist through the API and then refresh the current markdown render.
- Double-clicking a rendered non-diagram fenced code block opens an inline text editor for that block. When the editor loses focus, changed content is saved back to the original fenced section in the markdown file, then the current markdown render is refreshed. Backtick wrapper fences are resized during save so literal backtick runs inside the edited content cannot close the block early. If the content is unchanged, the editor is closed locally without calling the save API or refreshing the markdown render.
- API failure banners use the server-provided JSON `detail` when present. If a failed response is not JSON, the browser shows a fallback response text or generic operation message instead of a JSON parsing error.
- The viewer uses the browser viewport as the only page scrolling container;
  the app layout must not create a nested app scrollbar for normal markdown
  reading. The `markdown-table-wrap` horizontal scroll container (below) and
  the rendered code-block wrap/height-cap behavior (below) are the two
  explicit, bounded exceptions to this rule.
- The navigation toolbar is part of the page content flow above the rendered
  markdown, not a fixed app header.
- Light and dark theme toolbar surfaces use neutral grey colors instead of
  the bright primary-blue header.
- Dark theme uses a darker neutral grey toolbar background than the dropdown controls so
  the toolbar reads as chrome instead of a highlighted control.
- Toolbar dropdown controls use neutral grey surfaces in light, dark, and
  system modes for normal, hover, focused, and open states; they must not use
  saturated primary-blue standout styling.
- The theme dropdown is compact in the toolbar and uses a darker neutral grey
  control surface in dark or system-dark mode.
- Dark theme rendered content uses dark-appropriate surfaces for code blocks,
  inline code, tables, blockquotes, Mermaid diagrams, and maxGraph XML diagrams so default bright
  embedded backgrounds do not dominate the page.
- Rendered non-diagram fenced code blocks wrap long lines (including a single run with no natural
  break point, such as a long URL) at the markdown body width instead of scrolling horizontally.
  A block's visible height is capped at approximately 10 text rows (10× the block's line-height,
  plus its existing top/bottom padding); content beyond the cap scrolls vertically inside the block
  rather than growing the page. This applies to the rendered view only — the double-click inline
  code-block editor keeps its own wrap/resize behavior.
- Rendered markdown tables use content-sized automatic width rather than
  stretching to the full rendered body width.
- Rendered markdown tables must keep table display semantics; the table
  element itself must not use block-level layout that expands to fill its
  parent.
- Rendered markdown tables use readable spacing, restrained borders, distinct
  header treatment, and row striping in both light and dark themes. The table
  card visuals (background, border, rounded corners, shadow, vertical margins,
  body-width cap) are carried by a viewer-owned scroll container
  (`markdown-table-wrap`) around each table, which shrink-wraps narrow tables
  so the content-sized look is preserved.
- Rendered markdown tables must not extend beyond the markdown body content
  box. Cell text wraps at normal word boundaries; only a single word wider
  than its column may break mid-word (`overflow-wrap: break-word`). Because
  wrapping never erases a column's minimum content width, a column is never
  compressed below its longest unbreakable fragment by bulky sibling-column
  content. A table whose minimum width still exceeds the body content width
  scrolls horizontally inside its scroll container instead of overflowing the
  body or shredding a column.
- Rendered markdown images are constrained to the markdown body width while
  preserving their aspect ratio.
- In dark theme, Mermaid node and cluster fills and maxGraph XML diagram surfaces use neutral grey levels that
  sit above the diagram canvas without introducing colored background bias.
- Direct markdown paths remain supported through browser URLs and history, not
  through a separate toolbar path input or open button.

## Markdown Reading Typography
- Rendered markdown headings use smaller, restrained sizes than browser defaults so long markdown documents remain easy to scan in the viewer.
- Heading hierarchy remains visually distinct, with tighter spacing inside the rendered markdown body.
- Rendered body text uses a generous reading line height so prose stays comfortable to read across long documents.
- The rendered markdown body is presented as a padded, rounded content surface (its background and text colors following the active light or dark theme).
- The viewer column is horizontally centered and capped at a maximum reading width (`max-width: 15in` on the viewer shell) so rendered content does not stretch to the full window width on wide displays; on narrower windows it fills the available width.

## Browser Navigation
- Initial load uses the direct URL path when it names a markdown file, such as `/README.md` or `/docs/guide.md`.
- Initial load also accepts direct folder URL paths, such as `/docs`, for folder navigation.
- Initial load still accepts `?path=` as a backward-compatible fallback.
- Initial load enters the configured content root folder when neither a direct markdown URL nor `?path=` is present, rendering `README.md` first when it exists and otherwise rendering the first immediate markdown file in the root folder by case-insensitive filename sort order.
- Clicking rendered local `.md`, `.yml`, `.yaml`, `.json`, or `.jsonl` links prevents normal navigation and renders in-app (YAML links render as a collapsible YAML tree; JSON links render as a collapsible JSON tree).
- Clicking rendered `http` or `https` links, including same-origin absolute links whose URL path ends in `.md`, uses the original absolute URL as the final browser navigation target instead of in-app markdown rendering or app-relative URL prefixing.
- Successful in-app navigation pushes the response path into browser history as a direct URL; when folder navigation resolves to a markdown file, that markdown file path becomes the browser URL.
- Browser `popstate` reloads the file named by the current URL.
- Initial load and `popstate` navigation tolerate a URL that names a missing markdown file: when the render request fails for that direct/restored URL, the viewer falls back to rendering the configured content root (replacing the URL rather than pushing a new history entry) and surfaces a `File path does not exist: <url-relative path>` banner.
- The toolbar Home, Back, and Forward buttons and the `Alt+Left`/`Alt+Right` shortcuts (see "Browser UI") drive this same browser history/`popstate` mechanism rather than a separate navigation path: Home loads the configured content root, and Back/Forward step through the browser session history.

## In-Preview Content Search
- The feature is provided only when the viewer runs embedded in another browsing context (the VS Code preview hosts the viewer inside an iframe, detected as `window.self !== window.top`). In a normal top-level browser tab it is fully inert and the browser's native Ctrl+F is left untouched.
- When embedded, Ctrl+F (or Cmd+F) opens a floating find bar (top-right) and focuses its input, preventing the default browser find; pressing it again re-focuses and selects the input.
- Typing highlights every case-insensitive occurrence of the query in the rendered content (`.markdown-body`), debounced (~120ms after the last keystroke) so highlights refresh once typing pauses rather than on every key. HTML prose matches, including mermaid `foreignObject` HTML labels, are wrapped in `<mark class="md-search-hit">`. `<script>`, `<style>`, `<textarea>`, and already-highlighted text are skipped.
- SVG diagram text (maxGraph and mermaid `<text>`/`<tspan>` labels) is highlighted by splitting the matching characters into a `<tspan class="md-search-hit">` (best-effort substring tint; multi-line labels may tint imperfectly). Positioned tspans keep their attributes because only a leaf element's text children are split. Each split leaf element is tagged with a transient `md-search-host` bookkeeping class so the split can be reversed exactly on clear; that class is removed (and an emptied `class` attribute dropped) when highlights are cleared.
- A counter shows `current/total` (`0/0` with no matches). Enter or the down button moves to the next match, Shift+Enter or the up button to the previous, both wrapping around. The active match gets `md-search-hit--current` and is scrolled into view. Match order is document order across prose and diagrams together.
- Escape (from the find input or anywhere on the page while the bar is open) or the close button hides the bar and removes all highlights, restoring the original rendered DOM exactly (no leftover `<mark>`, sub-`<tspan>`, `md-search-host`, or other added class attributes).
- While the bar is open with a query, highlights are re-applied automatically after the content re-renders (auto-refresh) or diagrams finish rendering asynchronously, preserving the query and clamping the current index.
- The find bar and highlights have light and dark theme styling.
